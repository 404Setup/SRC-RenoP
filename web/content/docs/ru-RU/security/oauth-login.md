# Вход через сторонние сервисы

## Настройка провайдеров

В настройках администратора откройте **Сторонний вход**, чтобы настроить GitHub и другие сервисы. GitHub — встроенная
запись с постоянным ID `github`, которую можно включить или отключить. Допускается до 32 дополнительных клиентов с
уникальными ID длиной до 32 символов: строчные буквы, цифры, подчёркивания и дефисы, начиная с буквы. Сохранённые ID
определяют существующие привязки и не редактируются. Каждый аккаунт поддерживает одну привязку GitHub и до 32 других
привязок.

Для совместимости GitHub сохраняет `server.github_oauth` и адрес возврата `/api/auth/github/callback`. Существующие
настройки и привязки автоматически отображаются в общем интерфейсе. ID клиента ограничен 128 байтами, секрет — 512
байтами; пустой секрет сохраняет прежнее значение только при неизменном ID клиента. Авторизация пользователей и
организаций GitHub, подтверждённая почта и ручная синхронизация аватара остаются доступны.

Приведённые ниже сведения о конфигурации и протоколе относятся к дополнительным клиентам OAuth; GitHub сохраняет
существующий процесс авторизации и совместимый адрес возврата.

Зарегистрируйте у провайдера веб-приложение и разрешите точный адрес обратного вызова
`https://renop.example/api/auth/oauth/<provider-id>/callback`. Адреса OAuth и обратного вызова требуют HTTPS;
исключение — HTTP-адреса обратной петли для разработки. Сохранённые настройки сразу применяются к новой авторизации, а
уже начатые операции становятся недействительными при изменении конфигурации.

включите [отправку писем](../configuration/mail.md).

## Руководство по настройке провайдеров

### GitHub

Перейдите в GitHub в раздел **Settings** -> **Developer settings** -> **OAuth Apps** и нажмите **New OAuth App** (или
откройте Developer settings в настройках организации).

Заполните параметры приложения:

- **Application name**: Название приложения (например, `RenoP`).
- **Homepage URL**: Корневой URL вашего экземпляра RenoP (например, `https://renop.example`).
- **Authorization callback URL**: Выделенный URL обратного вызова GitHub
  `https://renop.example/api/auth/github/callback` (обратите внимание, что GitHub использует фиксированный маршрут, а не
  динамический подпуть).

Зарегистрируйте приложение, создайте **Client Secret** и сохраните **Client ID** и **Client Secret**. В панели
администратора RenoP в разделе **Сторонний вход** откройте встроенный пункт **GitHub**, укажите учетные данные и
включите его.

### Microsoft Entra ID

Войдите в центр администрирования Microsoft Entra или на портал Azure. Перейдите в **Удостоверение** ->
**Приложения** -> **Регистрация приложений** и выберите **Новая регистрация**.

Настройте параметры:

- **Имя**: Название приложения (например, `RenoP`).
- **Поддерживаемые типы учетных записей**:
    - Для поддержки личных и рабочих учетных записей: выберите «Учетные записи в любом каталоге организации и личные
      учетные записи Microsoft» и укажите `tenant: common` в RenoP.
    - Для рабочих учетных записей нескольких организаций: выберите «Учетные записи в любом каталоге организации» и
      укажите `tenant: organizations` в RenoP.
    - Только для личных учетных записей: выберите «Только личные учетные записи Microsoft» и укажите `tenant: consumers`
      в RenoP.
    - Только для текущей организации: выберите «Учетные записи только в этом каталоге организации» и укажите
      идентификатор (GUID) каталога в поле `tenant`.
- **URI перенаправления**: Выберите платформу «Web» и укажите `https://renop.example/api/auth/oauth/microsoft/callback`.

В разделе **Сертификаты и секреты** создайте новый секрет клиента и сразу сохраните его **Значение** (Value). В разделе
**Разрешения API** убедитесь в наличии делегированного разрешения `User.Read` с областями `openid`, `profile` и `email`.
В RenoP добавьте провайдера типа `microsoft`, указав Client ID, Client Secret и Tenant.

### Google Cloud

Откройте Google Cloud Console и перейдите в **API и сервисы** -> **Учетные данные**.

Если **Окно согласия OAuth** еще не настроено:

- Выберите тип пользователя **Внешний** (или Внутренний), укажите контактные данные и добавьте области `openid`,
  `.../auth/userinfo.email` и `.../auth/userinfo.profile`.

В разделе **Учетные данные** нажмите **Создать учетные данные** -> **Идентификатор клиента OAuth**:

- **Тип приложения**: Веб-приложение.
- **Разрешенные URI перенаправления**: Добавьте `https://renop.example/api/auth/oauth/google/callback`.

Сохраните и скопируйте **Идентификатор клиента** и **Секрет клиента**. В RenoP добавьте провайдера с типом `google`,
указав Client ID и Client Secret (области по умолчанию: `openid profile email`).

### GitLab

В GitLab.com или на собственном сервере GitLab создайте приложение OAuth:

- Для всего экземпляра: **Admin Area** -> **Applications**.
- В профиле пользователя: **User Settings** -> **Applications**.
- В группе: Группа **Settings** -> **Applications**.

Укажите параметры:

- **Name**: Название приложения.
- **Redirect URI**: `https://renop.example/api/auth/oauth/gitlab/callback`.
- **Confidential**: Оставьте флажок включенным.
- **Scopes**: Отметьте `openid`, `profile`, `email` и `read_user`.

Сохраните приложение и скопируйте **Application ID** (Client ID) и **Secret**. В RenoP добавьте провайдера с типом
`gitlab`. При использовании собственного сервера укажите `base_url` (например, `https://gitlab.example.com`).

### Cloudflare

В панели управления Cloudflare перейдите в **Управление аккаунтом** -> **Клиенты OAuth** (Manage Account -> OAuth
clients).

Нажмите **Создать клиент** (Create client) и настройте параметры приложения и протокола:

- **Client name**: Введите название клиента (например, `RenoP`).
- **Response type**: Поддерживаются Token, ID Token и Code (множественный выбор). **Обязательно отметьте `Code`** (RenoP
  использует поток кода авторизации).
- **Grant type**: Поддерживаются Authorization Code и Refresh Token (множественный выбор). **Обязательно отметьте
  `Authorization Code`**.
- **Redirect URLs**: Укажите полный URL обратного вызова RenoP, например
  `https://renop.example/api/auth/oauth/cloudflare/callback` (если вы изменили идентификатор провайдера, замените
  `cloudflare` на фактический).
- **Client URL** (необязательно): Домашняя страница RenoP (например, `https://renop.example`). Обязательно, если вы
  планируете позже перевести клиент в публичный (Public) статус (требуется подтверждение домена через запись DNS TXT);
  необязательно для частных (Private) клиентов, используемых только участниками вашего аккаунта Cloudflare.
- **Token authentication method** (один из трёх вариантов, должен совпадать с настройкой в RenoP):
    - **Client Secret POST** (по умолчанию и рекомендуется): Клиент передает секрет в теле запроса обмена токенов. В
      RenoP способ аутентификации токена по умолчанию установлен в `client_secret_post`.
    - **Client Secret Basic**: Клиент передает секрет через заголовок HTTP Basic Authorization. Если выбрано в
      Cloudflare, укажите в RenoP `client_secret_basic`. RenoP также автоматически согласует запасной вариант при
      получении ошибки HTTP 401.
    - **PKCE**: Публичный клиентский режим без секрета клиента. В RenoP выберите способ аутентификации `none` (секрет
      клиента не требуется).
- **Post-logout redirect URLs** (необязательно): Адрес перенаправления после выхода, например `https://renop.example`.
- **Allowed CORS origins** (необязательно): Разрешенные источники междоменных запросов; можно оставить пустым, так как
  обмен токенов выполняется сервером RenoP.

Нажмите **Continue** и настройте области разрешений (Scopes):

- Выберите необходимые права API для клиента (как минимум одно разрешение, например `User Details: Read`).
- **Настройка областей (Scopes)**: В настройках провайдера RenoP оставьте поле областей пустым (по умолчанию) либо
  укажите права, настроенные в Cloudflare (поддерживается разделение пробелами или запятыми, например
  `memberships.read, user-details.read, offline_access, openid`).
- **Автоматическая синхронизация почты и профиля**: При предоставлении разрешения `user-details.read` RenoP
  автоматически запрашивает API Cloudflare (`/client/v4/user`) при входе и регистрации для получения подтверждённого
  email и имени пользователя, пропуская шаг ручного ввода кода подтверждения. Если разрешение не выдано, новые
  пользователи авторизуются по идентификатору (`sub`) из `/oauth2/userinfo` и подтверждают почту кодом из письма RenoP.

После сохранения скопируйте **Client ID**, а также отображаемый в модальном окне только один раз **Client Secret** (при
использовании Client Secret POST или Client Secret Basic; обратите внимание, что это должен быть именно OAuth Client
Secret, а не API Token или Global API Key Cloudflare). В RenoP добавьте провайдера с типом `cloudflare`, указав Client
ID, Client Secret (при наличии) и соответствующий метод аутентификации токена (по умолчанию `client_secret_post`).
Лишние пробелы в начале и конце удаляются автоматически.

### Stack Exchange

Зарегистрируйте приложение на Stack Apps по адресу `https://stackapps.com/apps/oauth/register`.

Заполните форму:

- **Application Name**: Название приложения.
- **OAuth Domain**: Домен вашего сервера RenoP без схемы и порта (например, `renop.example`).
- **Enable Client Side Flow**: Оставьте флажок снятым.

Отправьте форму и сохраните **Client Id**, **Client Secret** и **Key** (ключ API для запросов и квот). В RenoP добавьте
провайдера с типом `stackexchange`, указав Client ID, Client Secret и API Key. Параметр `site` по умолчанию использует
`stackoverflow`.

### Пользовательские провайдеры

Для стандартных сервисов OpenID Connect или OAuth 2.0 (таких как Keycloak, Authentik, Authelia, Casdoor или Dex)
выберите тип `custom`.

Настройте конечные точки:

- **URL авторизации**: Конечная точка перенаправления для входа пользователя.
- **URL токена**: Конечная точка обмена кода авторизации на токен.
- **URL информации о пользователе**: Конечная точка для получения профиля JSON.
- **Издатель** и **URL JWKS**: Необходимы для проверки подписи OIDC.
- **Области**: Список областей через пробел (например, `openid profile email`).
- **Аутентификация токена**: Выберите `client_secret_post` или `client_secret_basic` в зависимости от провайдера.

Настройте сопоставление полей JSON:

- `subject`: Путь к уникальному стабильному идентификатору (например, `sub` или `id`).
- `username` и `name`: Пути к имени пользователя и отображаемому имени.
- `email` и `email_verified`: Пути к адресу электронной почты и флагу подтверждения.

## Конфигурация и учётные данные

Другие провайдеры хранятся в `server.oauth_providers`. В следующем примере клиенты отключены до замены учётных данных:

```yaml
server:
  oauth_providers:
    - id: microsoft
      type: microsoft
      name: Microsoft
      enabled: false
      client_id: ""
      client_secret: ""
      callback_url: https://renop.example/api/auth/oauth/microsoft/callback
      tenant: common
    - id: example
      type: custom
      name: Example Identity
      enabled: false
      client_id: ""
      client_secret: ""
      callback_url: https://renop.example/api/auth/oauth/example/callback
      authorize_url: https://identity.example/authorize
      token_url: https://identity.example/token
      userinfo_url: https://identity.example/userinfo
      scopes: ""
      token_auth: client_secret_post
      disable_pkce: false
      claims:
        subject: user.id
        username: user.username
        name: user.name
        email: user.email
        email_verified: user.email_verified
        avatar: user.picture
```

`name` допускает 80 байт UTF-8, `client_id` — 512 байт, секреты и ключи API — 4 096 байт. `scopes` — строка с
разделением пробелами длиной до 1 024 байт. URL допускают 2 048 байт. Встроенные шаблоны задают официальные адреса и
сопоставления полей; для других форматов используйте `custom`.

Собственные `claims` выбирают скалярные значения по путям JSON через точки и числовым индексам массивов, например
`user.id` или `items.0.id`. Длина пути — до 128 символов. `subject` должен быть стабильным идентификатором провайдера;
имена и адреса почты нельзя использовать как идентичность аккаунта. Числовые идентификаторы сохраняют точность.
Необязательные поля профиля можно пропустить. Строка `"true"` не подтверждает адрес почты.

Параметр `token_auth` собственного клиента принимает `client_secret_post`, `client_secret_basic` или `none`. PKCE S256
включён по умолчанию. `disable_pkce: true` разрешён только для собственного провайдера с секретом клиента. Для OpenID
Connect задайте `issuer` и `jwks_url` и добавьте `openid` в `scopes`; RenoP будет требовать и проверять токен
идентификации. Клиенты только OAuth используют аутентифицированный ответ с информацией о пользователе.

Собственные клиенты только OAuth включают путь поля идентичности в источник доверия. При изменении поля аккаунт нужно
привязать заново. Если такой клиент был включён начиная с коммита `26a1c1a`, повторная привязка нужна и после этого
обновления. Клиенты OIDC по-прежнему используют проверенный идентификатор субъекта токена. Cloudflare предоставляет
только `sub`, поэтому импорт почты и фотографии недоступен; данные регистрации вводятся вручную, а адрес подтверждается
кодом RenoP.

При чтении настроек возвращаются `client_secret_configured` и `api_key_configured`, а значения секретов остаются
пустыми. Пустое значение при записи сохраняет секрет только при совпадении ID, типа провайдера, ID клиента и адреса
получения токенов. `clear_client_secret` и `clear_api_key` явно удаляют данные. При смене клиента или адреса нужно
ввести их заново. Удаление провайдера блокирует новую авторизацию, но сохраняет привязки, чтобы пользователи могли
удалить их самостоятельно.

## Регистрация и управление аккаунтом

Вход через непривязанную внешнюю идентичность запускает [регистрацию аккаунта](./registration.md). Аккаунт и сеанс не
создаются, пока пользователь не подтвердит регистрацию и не задаст пароль. Для всех провайдеров действуют десятиминутный
срок подтверждения, период ожидания после истечения регистрации, квота по IP, политика получателей, местные ограничения
имён и псевдонимов и квоты аватаров. Совпадение адреса почты никогда не приводит к автоматическому выбору или
объединению существующих аккаунтов.

Ответ ожидающей регистрации содержит `provider`, `provider_name`, `email_required`, `mail_enabled` и `avatar_available`.
Если `email_required` равно true, пользователь должен ввести и подтвердить адрес, даже если провайдер предложил
неподтверждённый. Отправляйте `provider` вместе с `email` на адрес выдачи кода регистрации. При окончательном
подтверждении укажите тот же ID провайдера и полученный `code`. Повторная выдача кода не продлевает исходный срок и не
сбрасывает число ошибок. Если почта недоступна, регистрация через провайдера, требующего её подтверждения, не может
завершиться.

Если провайдер вернул подтверждённый адрес, он фиксируется на время регистрации и код не нужен. Импорт имени
пользователя, псевдонима и аватара необязателен; отсутствие фотографии или превышение её лимита не отменяет регистрацию.
Имена по-прежнему должны соответствовать ограничениям экземпляра, а занятое имя нужно заменить вручную.

В редакторе профиля можно привязать или обновить провайдера, импортировать его фото, использовать свежий подтверждённый
адрес или удалить привязку. Подтверждение почты требует новой авторизации и не меняет привязку входа. Для провайдеров
без поля подтверждения почты это действие не показывается. Импорт фото требует, чтобы выбранная внешняя идентичность
была привязана к текущему аккаунту. Перед отвязкой сервер сохраняет другой основной способ
входа. [Двухэтапная проверка](./two-step-verification.md), блокировки и окончательное закрытие аккаунта действуют и для
внешнего входа.

## API

| Метод  | Путь                                 | Контракт                                                                                       |
|--------|--------------------------------------|------------------------------------------------------------------------------------------------|
| GET    | `/api/auth/oauth/providers`          | Публичный список ID и названий настроенных провайдеров                                         |
| GET    | `/api/auth/oauth/:provider/start`    | `intent=login`, `register`, `link`, `email` или `avatar`; необязательный локальный `return_to` |
| GET    | `/api/auth/oauth/:provider/callback` | Одноразовый код авторизации и состояние, привязанное к браузеру                                |
| GET    | `/api/auth/profile/oauth`            | Частные состояния привязок, отображаемое имя, время авторизации и доступные действия           |
| DELETE | `/api/auth/profile/oauth/:provider`  | Отвязка: `204` или `409` с `oauth_last_login_method`                                           |
| GET    | `/api/settings/oauth-providers`      | Данные администратора: `providers` и `presets`, без секретов                                   |
| PUT    | `/api/settings/oauth-providers`      | JSON администратора `{providers:[...]}` заменяет список; тело до 128 KiB                       |

Операции профиля требуют текущего браузерного сеанса. Обратный вызов передаёт стабильный маркер результата в `oauth`, а
ID — в `provider`; SPA переводит сообщение и удаляет параметры. Ошибки никогда не показывают исходные ответы провайдера.
Метод входа записывается как `oauth:<provider-id>`, при необходимости с суффиксом `+totp` или `+passkey`.

## Авторизация Maven через GitLab

Авторизация GitLab.com за последний час может автоматически подтвердить новый домен `io.gitlab.<namespace>`. RenoP
принимает личное пространство аккаунта и группы верхнего уровня из утверждения GitLab о владении группами. Участие в
публичной группе, владение подгруппой и идентичности собственного экземпляра GitLab не подтверждают родительское
пространство или пространство GitLab.com. Обновите привязку для обновления доказательства владения. Для каждой
идентичности хранится до 1 001 пространства имён. Проверка через публичную биографию или описание группы остаётся
доступной.

## Безопасность и эксплуатация

Обратные вызовы OAuth используют HttpOnly cookie со сроком десять минут, одноразовое состояние сервера и PKCE. Хранится
до 2 048 состояний внешней авторизации. Изменение конфигурации отменяет ожидающие обратные вызовы и регистрации. OIDC
проверяет подпись, издателя, аудиторию, субъекта, nonce, временные ограничения и хеш токена, если он предоставлен;
поддерживаются RS256 и ES256. Ответы ограничены 1 MiB, запросы имеют конечные тайм-ауты. Используется настроенный
исходящий прокси.

RenoP связывает стабильные идентификаторы субъекта с источником доверия, вычисляемым из типа провайдера, клиента,
адресов и проверенного издателя. Изменение этого источника не переносит существующие привязки к другому сервису
идентификации. Токены доступа для входа не сохраняются. Для защищённого аватара зашифрованный токен может временно
храниться только в ожидающей регистрации до подтверждения или истечения срока; его защищает частный
`mfa_encryption_key`. Браузеру он никогда не возвращается.

Закрытие аккаунта атомарно освобождает все сторонние привязки. Другой действующий аккаунт может привязать освобождённую
идентичность, но старое имя остаётся зарезервированным навсегда, почта удерживается 14 дней, а активность — 30 дней.
Запоздавший обратный вызов или обновление не может восстановить привязки закрытого аккаунта.

Для новой привязки одновременно должны быть доступны внешняя идентичность и все полученные контактные адреса.
Освобождённая идентичность не обходит владение адресами, удерживаемыми другим аккаунтом. Правила подтверждения, удаления
и хранения описаны в разделе [дополнительных адресов для входа](./email-verification.md).
