# 故障排查

先确认 HTTP 状态、准确 URL、仓库格式与可见性，以及使用的凭据类型。不要一次修改多个设置：包管理客户端往往会用
自己的通用错误掩盖服务器原始响应。

## 收集最少必要证据

在重启或删除状态前记录：

- RenoP 版本与启动时间；
- 请求时间、方法、脱敏 URL 和响应状态；
- 仓库名称、格式、可见性，以及是否涉及镜像或发布审核；
- 客户端名称与版本、命令，以及已移除密钥的详细日志；
- 相关服务日志；若响应包含 `X-Renop-Error-Code`，一并记录；
- 数据库和存储可达性、剩余空间与最近配置变更。

不要在问题单或聊天记录中粘贴会话 Cookie、API 令牌密钥、密码、S3 密钥、OAuth 密钥或完整授权请求头。

## 进程无法启动

先检查配置路径与工作目录。`config.yaml`、`repositories.yaml`、SQLite 数据库、`index.json` 与本地存储使用
相对路径时，会相对于服务运行环境解析；这可能和交互式终端不同。

常见原因包括监听端口被占用、YAML 格式错误、数据库 DSN 不可达、缺少写权限、TLS 文件无效，或服务账户无法读取
密钥。初始管理员密码只影响账户初始化；修改 `RENOP_DEFAULT_ADMIN_PASSWORD` 不会重置已存在的管理员。

## 健康检查正常，但应用仍失败

```bash
curl -i https://packages.example.com/api/status/health
```

`"UP"` 只表示进程能够提供健康检查路由，不会验证登录、数据库写入、本地或 S3 存储、镜像访问或发布策略。请继续
执行一次经过认证的浏览器请求，并在受影响后端上使用一次性包完成操作。

若 Web 界面提示存在新版界面，请先重新加载，再排查 protobuf 解码或路由缺失问题。反向代理或浏览器缓存可能仍在
提供与服务器版本不一致的 JavaScript。

## 先看状态码，再看错误文本

| 状态  | 首要检查项                                                             |
|:------|:-----------------------------------------------------------------------|
| `400` | protobuf/JSON 格式错误、路径或名称无效、缺少必填字段、操作不受支持     |
| `401` | 凭据缺失、过期、格式错误或类型不允许；Cookie 未通过 HTTPS/代理返回     |
| `403` | 账户权限、令牌作用域/目标、团队级别、仓库可见性、调试模式或审核角色    |
| `404` | 仓库或路径错误、资源隐藏、版本不存在、镜像未命中，或私有数据被刻意隐藏 |
| `409` | 不可变版本/标签冲突、名称已预留、状态转换冲突或并发决策                |
| `413` | 反向代理或服务端上传限制；检查镜像层/制品大小与缓冲设置                |
| `429` | 速率或并发控制；遵循重试提示并降低并行度                               |
| `5xx` | 数据库、存储、上游、签名、解压或内部故障；检查服务日志                 |

纯文本错误面向人工阅读，可能随版本调整。程序应使用状态码、协议原生结构化响应，以及存在时的稳定错误头。

## 身份认证与浏览器会话

管理界面使用 HttpOnly `renop_session` Cookie。私有账户安全端点不接受密码、Bearer 令牌、
`Authorization: Session` 或 URL 中的会话值。确认公开来源使用 HTTPS，代理转发原始协议与主机，浏览器也能将
Cookie 返回到同一来源。

自动化应使用有作用域的 Bearer API 令牌。实际权限是令牌作用域、目标限制、账户当前权限、仓库策略与包团队成员
资格的交集。重新签发作用域更大的令牌，不能修复缺失的账户或团队权限。

## Maven 与 Gradle

- 确认仓库 URL 以 RenoP 仓库名结束，而不是 `/api`。
- Maven `<server><id>` 必须与 `distributionManagement` 或依赖仓库中使用的 ID 完全一致。
- Basic 用户名使用账户名，密码位置使用具备所需作用域的 API 令牌。
- 确认 `groupId` 位于账户控制的发布域下，并具备所需团队级别。
- 对要求签名的仓库，上传所需的分离签名，并检查后端签名记录，不要只根据文件名判断。
- 正式版重新部署或其他不可变发布应被拒绝；不要通过直接删除服务端文件规避策略。

## Cargo

- 使用包含仓库路径且以斜杠结尾的稀疏索引 URL，例如 `sparse+https://packages.example.com/crates/`。
- 运行 `cargo login --registry <name>`，并保存 Cargo 所需的完整 RenoP 令牌值。
- 区分 `repository:publish`、`package:create`、生命周期与团队管理作用域。
- 首次发布时，如果上游名称检查不可用，服务会安全失败；恢复上游连接后重试，不要假设名称已经预留。
- 发布审核待处理期间，已接收的归档不会出现在稀疏索引或公开目录中。

## npm

- 将 registry 设置为仓库路径，而不只是主机；需要时为 scope 单独配置 registry。
- 检查用户或 CI `.npmrc` 中准确的令牌条目，不要将其提交到项目。
- 仓库策略要求时，在首次发布前预留包名。
- 版本发布不可变；重试并提高并发不会修复版本冲突。
- 对镜像包进行团队或 dist-tag 变更前，先确认目标版本来自上游还是本地拥有的包。

## Docker 与 OCI

- 登录 registry 主机；镜像名与仓库路径应分别提供给 `pull`、`push` 或 Podman。
- 使用客户端信任的证书。只有隔离测试环境才应配置不安全 registry。
- 首次推送前，按 RenoP 策略创建或预留所需镜像/命名空间。
- 反向代理必须保留 `/v2/` 质询和 `/v2/token` 交换。移除 `Authorization` 或重写路径会破坏 Bearer 流程。
- 推送失败时，确认被拒绝的是 blob、manifest 还是 tag，并将其摘要和媒体类型与服务响应对照。

## 镜像、存储与反向代理

镜像未命中可能来自上游 `404`、负缓存、允许列表拒绝、凭据过期、出站代理故障或本地提交失败。可在 RenoP 主机上
比较直接访问上游与经过 RenoP 的同一请求，但不要在生产环境中通过绕过认证来完成测试。

S3 兼容存储应检查端点、区域、路径风格、存储桶、前缀、时钟同步、TLS 信任，以及读/写/列举/删除权限。预签名
重定向应从客户端网络验证返回地址。本地存储应检查所有者、剩余空间、临时文件容量与文件系统原子重命名行为。

大文件上传需要关闭请求缓冲、移除请求体限制并延长读写超时。只信任已配置代理提供的转发请求头，否则速率限制与
审计 IP 可能被伪造。

## 使用可复现案例升级处理

将故障缩小到一个仓库、一个一次性包和一条命令。提供脱敏配置、预期与实际状态，并说明绕过反向代理直接访问 RenoP
时是否正常。列出已尝试的恢复操作。在证据收集完成前，不要通过删除数据库、存储前缀或包所有权来让症状消失。

API 客户端行为参见 [HTTP API 集成](../api/client-integration.md)；部署验证参见
[生产部署检查清单](../deployment/production-checklist.md)。
