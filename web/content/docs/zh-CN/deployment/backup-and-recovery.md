# 备份、恢复与迁移

只有当配置、仓库策略、数据库状态和不可重建的制品数据能够作为一个整体恢复时，RenoP 备份才算完整。只复制
`index.json` 或一个 S3 存储桶并不充分。

## 对数据进行分类

| 数据            | 常见位置                                    | 恢复作用                                       |
|:----------------|:--------------------------------------------|:-----------------------------------------------|
| 主配置          | `config.yaml` 或 `RENOP_CONFIG`             | 监听、数据库、代理、安全、预览、更新器         |
| 仓库定义        | `repositories.yaml` 或 `RENOP_REPOSITORIES` | 格式、可见性、镜像、存储后端、策略             |
| 数据库          | `renop.db` 或外部 DSN                       | 账户、权限、会话、令牌、团队、审核、审计、消息 |
| 本地制品数据    | `storage_path`                              | 已发布包、上传内容、上游缓存                   |
| S3 兼容制品数据 | 存储桶及各仓库前缀                          | S3 后端仓库的已发布包与缓存内容                |
| 文件索引        | `index.json` 或 `RENOP_INDEX`               | 性能快照；建议保留，但可从权威数据重建         |
| TLS 与集成密钥  | 代理或密钥管理系统                          | 恢复同一公开服务与外部集成所需                 |

官网构建输出、已下载的前端依赖和构建缓存都可以重新生成，不应成为任何运维密钥的唯一副本。

## 选择一致性时间点

最稳妥的通用方案是冷备份：阻止新流量，正常停止 RenoP，创建数据库与制品后端快照，复制配置，然后重新启动。
这样可以避免数据库记录与在不同时间捕获的对象不一致。

若无法停机，应使用事务一致的数据库备份与存储快照，并记录共同恢复点。SQLite 使用预写日志时，已提交数据可能
仍位于 WAL 文件中，因此只在线复制主数据库文件并不安全。多个供应商快照仅仅在相近时间开始，并不表示它们彼此一致。

## 备份本地 SQLite 部署

使用启动 RenoP 的同一服务管理器停止进程。进程完全退出后，复制已关闭的数据库、配置、仓库文件、索引快照与本地
存储目录。

```bash
install -d /backup/renop
cp config.yaml repositories.yaml renop.db index.json /backup/renop/
rsync -a storage/ /backup/renop/storage/
```

实际路径应以 `RENOP_CONFIG`、`RENOP_REPOSITORIES`、`RENOP_INDEX`、数据库 DSN 与 `storage_path` 为准；示例中
使用的是默认名称。应保留文件所有者、权限和必要的扩展属性，并为临时上传文件预留足够空间。

## 备份外部数据库

使用数据库供应商支持的逻辑导出、物理备份或托管快照机制。备份必须包含全部 RenoP 表和迁移元数据。加密备份流量
与备份文件，记录 RenoP 版本和数据库引擎版本，并使用供应商恢复工具验证备份。

对于 MySQL 或 PostgreSQL，应优先使用能够在同一事务或恢复点覆盖全部表的一致性快照。对于 ClickHouse，请遵循
所用部署方式的运维要求，并保留 RenoP 事务日志恢复所需的数据。数据库丢失后，不要尝试仅通过 Web 界面重新拼出
账户或团队状态。

## 备份本地与 S3 兼容制品

本地存储应复制完整的配置根目录。不要按文件扩展名筛选：元数据、清单、包索引、签名与上传状态可能和主归档同样重要。

对于 S3 兼容存储：

- 保护每个仓库使用的存储桶与 `key_prefix`。
- 在服务支持时启用版本控制或复制，并实际验证对象恢复，而不只是对象列举。
- 备份凭据应与 RenoP 日常使用的凭据分离。
- 保留对象元数据，并确认生命周期规则不会过早删除唯一保留副本。
- 除非预签名下载设计明确要求，否则保持存储桶私有。

镜像缓存通常可以重新填充，但本地发布的制品可能无法替代。只有在能够可靠区分二者后，才应采用不同的保留策略。

## 在隔离环境中恢复

首先恢复到隔离主机或网络。使用创建备份时的 RenoP 版本，确认恢复后的服务正常，再将升级作为独立步骤执行。

1. 恢复 `config.yaml`、`repositories.yaml`、证书和集成密钥，并设置严格权限。
2. 恢复数据库，确认配置的主机名、凭据和 TLS 设置仍有效。
3. 恢复本地存储，或重新连接完全相同的 S3 存储桶与前缀。
4. 若有 `index.json` 则恢复；否则允许 RenoP 从权威存储重建索引。
5. 在不接入公开流量的情况下启动 RenoP，并检查启动错误。
6. 登录、列出仓库，并测试代表性的包读取。
7. 使用最小作用域令牌发布并删除一个一次性包。
8. 只有在认证、镜像、审核、配额、预览和审计记录均验证通过后，才重新开放流量。

发生安全事件后，恢复仍然有效的会话与令牌可能并不合适。应根据事件范围撤销会话、轮换 API 令牌，并更换数据库、
存储、OAuth、SMTP、代理与签名凭据。

## 迁移仓库存储后端

使用 RenoP 的仓库管理迁移流程，使仓库操作与后端切换串行协调。不要在 RenoP 运行时直接编辑物理目录、在后台复制
活动对象，或在数据复制完成并验证前切换配置。

迁移前记录包与版本数量、总字节数、仓库策略、源与目标设置以及可用容量。迁移后比较清单与代表性哈希，使用原生客户端
测试读写，并在验收期结束前将源端保留为只读回滚副本。

## 定期进行恢复演练

为完整服务定义恢复点目标和恢复时间目标，而不是只针对数据库。至少应定期将最新备份恢复到空白环境，并记录：

- 备份开始与完成时间；
- RenoP、数据库和存储服务版本；
- 恢复耗时与人工步骤；
- 每种启用格式的包读写验证结果；
- 缺失对象、权限错误、陈旧 DNS 或证书，以及后续处理事项。

从未恢复过的备份只是未经验证的假设。请将最终运行手册链接到[生产部署检查清单](./production-checklist.md)，
并保存一份停机期间仍可访问的离线副本。
