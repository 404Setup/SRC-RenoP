# 生产部署检查清单

请在首次启动成功后、允许制品客户端或不受信任网络访问服务前完成本清单。健康检查通过只是必要条件，
不能证明身份认证、数据库、存储、镜像或发布策略已经端到端可用。

## 明确服务边界

记录公开主机名、监听地址、反向代理、数据库、存储后端与仓库负责人。应将 RenoP 视为一个需要统一协调的
服务。外部数据库或 S3 兼容后端可以替代本地状态组件，但本身不会自动提供安全的主动-主动协调能力。

- 指定一名运维负责人和一名安全联系人。
- 记录 RenoP 版本、配置路径、服务账户、工作目录与更新通道。
- 在发布客户端配置前，确定各仓库是公开、隐藏还是私有。
- 除非已经完整验证所有公开来源的代理与 Cookie 行为，否则管理界面和制品端点应使用同一个规范 HTTPS 来源。

## 保护初始化与账户恢复能力

`RENOP_DEFAULT_ADMIN_PASSWORD` 只应用于首次创建 `admin` 账户。若 RenoP 自动生成了密码，请从首次启动日志中
取得并立即更换。

- 日常管理应使用实名管理员账户，不要多人共用 `admin`。
- 在禁用密码登录前，注册通行密钥或配置并验证另一种可用登录方式。
- 生成恢复代码，离线保存，并确认账户邮箱正确。
- 为各 CI 任务分别签发有有效期的 API 令牌，只授予任务所需的作用域与仓库目标。
- 将数据库、S3、OAuth、SMTP、签名和出站代理凭据保存在密钥管理系统或受保护的服务环境中。

## 通过 HTTPS 发布服务

由反向代理终止 TLS 时，将 RenoP 绑定到回环或私有地址。配置公开主机名，并且只信任确实有权提供客户端
IP 请求头的代理地址。

```yaml
server:
  host: "127.0.0.1"
  port: 3000
  domains:
    - "packages.example.com"
  trusted_proxies:
    - "127.0.0.1"
  cdn_ip_header: "X-Forwarded-For"
```

代理必须保留 `Host`、原始协议和客户端地址链。对于大文件上传，应关闭请求缓冲，移除意外的请求体大小上限，
并为镜像层和大型制品设置足够长的读写超时。不要信任任意客户端提交的转发请求头。参见
[反向代理](./reverse-proxy.md)。

## 保护数据库与制品存储

选择适合部署环境的数据库，并通过一次真实的认证写入验证。使用 SQLite 时，应将数据库放在持久化本地存储上，
并确保服务账户拥有数据库文件及其目录。使用外部数据库时，应在支持的情况下启用加密传输，并限制只有 RenoP
可以访问数据库网络端点。

逐个确认仓库使用的本地或 S3 兼容后端、存储桶或目录、前缀、凭据与下载模式。预签名重定向地址必须能从客户端
网络访问且处于可信范围；代理流式下载可保持存储桶私有，但全部制品流量会经过 RenoP。

制定能够将配置、仓库定义、数据库和不可重建的制品数据作为同一恢复集保存的备份流程，并实际进行恢复演练。
参见[备份、恢复与迁移](./backup-and-recovery.md)。

## 定义仓库与发布策略

- 为每个仓库选择正确格式；不同客户端协议不可互换。
- 复核可见性、读取与发布权限、团队成员、命名空间所有权、配额和发布审核策略。
- 有目的地配置镜像。应根据上游设置超时、缓存期限、负缓存和允许列表，而不是默认信任公共仓库。
- 在公布发布地址前，验证 Maven 发布域；按策略预留 npm 包与 Docker 镜像名称；确认 Cargo 名称可用。
- 明确谁可以批准发布审核，以及谁可以处理所有权转移任务。

## 使用原生客户端验证

使用将实际发给用户的主机名、凭据、仓库名和代理路径进行测试。每种启用的格式至少完成一次读取和一次授权写入。
若已启用生命周期权限，还应使用一次性包测试删除、yank、归档或标签变更。

```bash
curl --fail-with-body https://packages.example.com/api/status/health
```

预期响应体为 `"UP"`。

还应确认：匿名请求无法读取私有仓库；作用域不足的令牌会被拒绝；隐藏仓库不会出现在发现结果中；过大或不符合
策略的发布会失败，且不会留下对外可见的部分状态。

## 建立运维与监控机制

- 监控进程可用性、存储容量、数据库状态、证书过期时间、上游延迟，以及重复出现的认证或发布失败。
- 将服务日志保留在应用工作目录之外，并按可能包含敏感信息的数据加以保护。
- 定期检查审计日志与站内消息；二者都不能代替外部告警。
- 在非生产环境中验证所选正式版或 Nightly 更新流程，再启用自动更新。
- 设定维护窗口，并记录谁有权撤销会话、令牌或被入侵的包所有权。

## 上线检查清单

- [ ] 所有必需的客户端网络都能解析并访问规范 HTTPS 主机名。
- [ ] 已用大型上传验证代理请求体限制、缓冲、超时和转发请求头。
- [ ] 管理员恢复方式与离线恢复代码可用。
- [ ] CI 使用有作用域和有效期的令牌，而不是个人密码。
- [ ] 数据库及每个制品后端都通过了写入、读取与删除测试。
- [ ] 已复核仓库可见性、所有权、配额、镜像与审核策略。
- [ ] 私有仓库通过直接地址和代理地址访问时均保持私有。
- [ ] 备份位于独立故障域，且恢复演练成功。
- [ ] 容量和证书告警有明确接收人。
- [ ] 已记录当前二进制文件、配置与回滚流程。

## 在变更生产环境前准备回滚

在新版本通过客户端验证前，保留此前可用的二进制文件、配置文件与数据库/存储备份。回滚时，应同时恢复彼此兼容的
应用版本与数据快照；不要假设被新版本迁移过的数据库一定能由旧版二进制继续使用。每次回滚都应记录原因、时间与
受影响仓库。

如需验证具体协议，请继续阅读 [Maven](../guides/maven-client.md)、[Cargo](../guides/cargo-registry.md)、
[npm](../guides/npm-registry.md) 与 [Docker/OCI](../guides/docker-registry.md) 指南。
