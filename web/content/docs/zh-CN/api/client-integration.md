# HTTP API 集成

RenoP 在同一服务端口下统一提供管理端点与多协议包客户端路由。
发起请求前需明确接口类别，原生包客户端与通用管理 API 采用不同的路由和认证规范。

## 选择正确的 API 表面

| 表面                    | 常见路径                                    | 预期客户端                       |
|:------------------------|:--------------------------------------------|:---------------------------------|
| 管理与浏览器 API        | `/api/...`                                  | RenoP 界面、管理工具、自动化程序 |
| Maven 与通用文件        | `/{repo}/{path}`                            | Maven、Gradle、HTTP 制品客户端   |
| Cargo 稀疏仓库          | `/{repo}/config.json`、`/{repo}/api/v1/...` | Cargo 与兼容工具                 |
| npm registry            | `/{repo}/{package}`、`/{repo}/-/...`        | npm 兼容客户端                   |
| Docker/OCI Distribution | `/v2/...`、`/v2/token`                      | Docker、Podman、OCI 客户端       |
| 文档预览                | `/javadoc/...`、`/cargodoc/...`             | 仓库授权后的浏览器               |

原生包客户端通常直接使用仓库名或协议专属前缀（如 `/{repo}/...` 或 `/v2/...`），
请勿在包协议路由前添加 `/api`；管理 API 则统一以 `/api` 前缀暴露。

## 使用声明的表示格式

基于消息模式的管理 API 支持 JSON（`application/json`）和二进制 protobuf（`application/x-protobuf` 或
`application/protobuf`）。`Content-Type` 决定请求解码方式，`Accept` 决定响应格式。未指定或不支持的 `Accept`
会保留旧客户端使用的 protobuf 响应；未指定请求类型时也沿用 protobuf 解码。消息定义见 `proto/api/v1/api.proto`。

```http
Content-Type: application/x-protobuf
Accept: application/x-protobuf
```

请求与响应均使用 JSON 时，请同时设置两个请求头：

```http
Content-Type: application/json
Accept: application/json
```

JSON 输出使用原始 snake_case 字段名，输入也接受 protobuf 的 camelCase 名称。64 位整数使用十进制字符串，
字节字段使用 Base64 字符串。未知或重复的 JSON 字段会被拒绝。控制请求仍限制为 1 MiB，并保留端点原有的
更小上限。原生仓库协议、上传二进制分块、健康检查纯文本与各端点的错误格式维持原状。

## 根据调用方选择凭据

| 凭据                   | 用途                               | 重要限制                             |
|:-----------------------|:-----------------------------------|:-------------------------------------|
| `renop_session` Cookie | 交互式浏览器界面与私有账户安全操作 | HttpOnly；不要提取后在脚本中重放     |
| Bearer API 令牌        | 管理自动化与支持 API 令牌的路由    | 实际权限与账户和团队当前权限取交集   |
| HTTP Basic             | 包客户端与指定上传流程             | 不能普遍替代浏览器会话或 Bearer 令牌 |
| Docker Bearer 令牌     | Docker/OCI Distribution 操作       | 通过 registry 质询与令牌交换取得     |

令牌密钥通常只在创建时显示一次。应存入密钥管理系统，设置有效期，限制目标与作用域，并在任务或设备退役时撤销。
查询字符串凭据和 `Authorization: Session` 会被拒绝。

## 正确构造基础 URL

生产环境应使用一个规范 HTTPS 来源。反向代理需保留原始 `Host` 与协议，使 Cookie、重定向、Docker 质询和生成的
仓库 URL 均指向公开服务。

```bash
curl --fail-with-body https://packages.example.com/api/status/health
```

成功响应体为 `"UP"`。

健康端点适合检查可达性，但不能证明数据库或存储能够提交数据。若部署自动化必须验证这些依赖，应另行执行经过认证的
就绪操作。

## 按稳定顺序处理响应

1. 读取 HTTP 状态。
2. 检查响应 `Content-Type`。
3. 存在时读取 `X-Renop-Error-Code`。
4. 只使用与协议匹配的解码器处理响应体。
5. 记录关联时间与脱敏请求上下文，绝不记录凭据。

管理端点错误通常返回标准状态码与简短说明；各包管理器端点则严格沿用各自官方生态的结构化错误。
客户端应优先基于 HTTP 状态码或响应头中的专用错误码编写处理逻辑。

## 将状态映射为客户端行为

| 状态        | 客户端处理                                                           |
|:------------|:---------------------------------------------------------------------|
| `200`–`204` | 按文档声明的响应类型解码；端点规定成功时返回空响应体也是有效结果     |
| `202`       | 视为已接收但不一定已可见；发布审核可能仍在等待                       |
| `302`       | 只对文档明确说明的下载重定向跟随，例如已授权的 S3 预签名地址         |
| `400`       | 修正请求；自动重试通常只会重复同一错误                               |
| `401`       | 先确认目标路由允许该凭据类型，再刷新或更换凭据                       |
| `403`       | 不要盲目重试；需调整作用域、目标、账户权限、团队级别、策略或调试模式 |
| `404`       | 检查路径与可见性；私有或隐藏数据可能被刻意隐藏                       |
| `409`       | 重新读取状态，再判断不可变操作或并发操作是否能够调整                 |
| `413`       | 仅在业务允许时缩小请求体，否则修复代理/服务端限制                    |
| `429`       | 遵循重试提示，加入抖动并降低并发                                     |
| `5xx`       | 只对有界且安全的操作重试；保留原始错误并检查服务依赖                 |

## 只在语义允许时重试

GET 和 HEAD 在传输失败后通常可以安全重试。对于写入，应先确认端点或包协议是否幂等，以及连接中断前服务是否可能
已经提交请求。使用带抖动的有界指数退避，并设置总截止时间。

不要通过静默更换版本号、删除数据或扩大凭据权限来重试不可变发布。对于分块上传或 registry 上传，应继续使用协议
自身的上传状态，而不是重放无关步骤。

## 遵循端点各自的分页与过滤规则

列表端点没有统一的游标或分页模型。使用该端点文档中的参数，保留服务器返回的稳定标识，并在响应表明结束时停止。
在支持时由服务端执行过滤，但不要假设界面过滤会改变认证或仓库可见性。

## 使用同一版本的契约文件

`web/assets/openapi.yaml` / `proto/api/v1/api.proto`

请使用与已部署版本配套的 OpenAPI 和 protobuf 定义。ProtoJSON 的整数和字节表示遵循上述规则；原生包客户端
继续使用各自的协议配置。

升级生产环境前，应在非生产实例上测试登录、令牌授权、仓库列表、每种启用格式的一次代表性读写、分页、错误解码和
反向代理行为。

## 集成检查清单

- [ ] 已选择正确的 API 类型与仓库基础路径。
- [ ] HTTPS 来源、代理主机与协议均为规范值。
- [ ] 请求与响应媒体类型均已明确设置。
- [ ] 目标路由允许所用凭据类型。
- [ ] 令牌作用域、目标、有效期和所有者权限保持最小且仍然有效。
- [ ] 在解析响应文本前先处理状态码。
- [ ] 重试有次数上限、包含抖动，并且对当前操作安全。
- [ ] 日志会脱敏 Cookie、密码、令牌和签名 URL。
- [ ] OpenAPI 与 protobuf 文件匹配已部署版本。
- [ ] 部署前运行协议原生的端到端测试。

路由级细节与故障诊断参见[身份认证 API](./authentication.md)、[API 令牌与用户](./tokens.md)和
[故障排查](../guides/troubleshooting.md)。
