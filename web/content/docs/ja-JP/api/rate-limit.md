# レート制限と異常検知

グローバル ミドルウェア（`AnomalyMiddleware`）がルートハンドラの前にすべてのリクエストで動きます。実装:
`middleware/anomaly.go`。

3 つの独立した制御が順に適用されます:

1. **同時リクエスト上限** — プロセス全体
2. **認証失敗バン** — クライアント IP ごと
3. **匿名リクエスト レート制限** — クライアント IP ごと（トークンバケット）

制限が発動すると、レスポンスに `Connection: close` が付く場合があります。

## クライアント IP

制限のキーは `utils.ExtractIP` から得たクライアント IP です:

- 既定: ピアアドレス（`c.IP()`）。
- ピアがループバック（`127.0.0.1` / `::1`。同一ホスト上の Caddy/nginx で典型）または
  `server.trusted_proxies` に含まれ、 **かつ** `server.cdn_ip_header` が設定されている場合、そのヘッダーから クライアント
  IP を取得します（複数値ヘッダーは右から左へ、信頼済みホップをスキップ）。

プロキシ信頼の設定ミスは、多くのユーザーを 1 IP にまとめたり逆を引き起こします。サーバー設定は
[settings.md](./settings.md) を参照。

Cloudflare → Caddy → RenoP の場合は `cdn_ip_header` を `CF-Connecting-IP` に設定すれば十分です。 ループバックのピアは
`trusted_proxies` への追記が不要です。

## 1. 同時リクエスト上限

| 設定                         | デフォルト | 効果                             |
|------------------------------|------------|----------------------------------|
| `server.max_active_requests` | `2000`     | プロセス全体のインフライト最大数 |

- ミドルウェアに入る **すべて** のリクエストを数えます（認証済み・静的を含む）。
- 上限を超えそうなとき → **`503 Service Unavailable`**。
- 設定の `0` は読み込み時に既定（`2000`）へ正規化。このフィールドでの「無制限」はありません。

Fiber 自身の同時実行上限も起動時にこの値に合わせます。

## 2. 認証失敗バン（IP ごと）

| 定数                   | 値   | 意味                              |
|------------------------|------|-----------------------------------|
| `MaxFailuresPerMinute` | `5`  | バン前の失敗回数しきい値          |
| Failure store TTL      | 5 分 | `AnomalyFailures` BigCache の寿命 |

**何が失敗として数えるか**

ハンドラ実行後、最終ステータスが **`401`** または **`403`** なら、IP ごとの失敗カウンタが増えます（キャッシュ内の 8 バイト
little-endian カウンタ）。

**バンの挙動**

- リクエスト開始時にカウンタが既に **≥ 5** → 直ちに **`403 Forbidden`**（ハンドラは走らない）。
- バン応答は `Next()` の前に返るため、カウンタは再増加しません。
- キャッシュ TTL は最終書き込みから **5 分**（記録された失敗ごとにエントリが更新）。期限切れ後は カウンタが消え、IP
  は再試行できます。

**範囲**

静的フロントエンド スキップ（下記）を通過する **すべて** のパスに適用（認証済みクライアント含む）。ハンドラから 401/403
を受け続けるクライアントは、後続リクエストの資格情報に関係なくこのバンに達します。

注: 定数名は「per minute」ですが、ストア窓は **5 分** で、エントリ期限までカウンタは増加するだけです。

## 3. 匿名リクエスト レート制限（IP ごと）

`golang.org/x/time/rate` のトークンバケット。IP ごとに 1 リミッタ（`GlobalIPLimiter`）。

| 定数                   | 値    | 意味                                            |
|------------------------|-------|-------------------------------------------------|
| `MaxRequestsPerMinute` | `100` | 持続レート: 100 トークン / 分（約 600 ms に 1） |
| `MaxRequestsBurst`     | `60`  | バースト容量（同時に保持できる最大トークン）    |

- **制限対象:** 認証済みと検証されていないリクエスト（下記）。
- **免除:** 正常に検証された Session / Bearer / Basic（または有効なセッション / bearer に解決する GET/HEAD `?token=`）。
- **超過時:** **`429 Too Many Requests`**。

### 「検証済み認証」とは

本番の認証搬送手段と同じ考え方（[authentication.md](./authentication.md) 参照）:

| 搬送手段                                          | 検証されるとき                                    |
|---------------------------------------------------|---------------------------------------------------|
| Cookie `renop_session` / `Authorization: Session` | セッションが存在しアイドル時間内                  |
| `Authorization: Bearer <user>:<secret>`           | ユーザー名 + secret が有効アカウントに一致        |
| `Authorization: Bearer <upload-token>`            | トークンが索引済みで未期限切れ                    |
| `Authorization: Basic …`                          | ユーザー名 + パスワード/secret が一致             |
| GET/HEAD `?token=`                                | トークンが有効なセッション id または上記の bearer |

存在するが **無効な** 資格情報は免除しません。レート制限トークンを消費し、ハンドラが 401/403 なら失敗カウンタも上がります。

アイドル期限切れのセッションは認証済みとみなしません（アイドル約 7 日。認証ドキュメント参照）。

### リミッタのライフサイクル

| 動作               | 詳細                                                   |
|--------------------|--------------------------------------------------------|
| キー               | クライアント IP 文字列                                 |
| アイドル削除       | **5 分** 未使用のエントリを削除                        |
| 定期クリーンアップ | **5 分** ごと                                          |
| 緊急クリーンアップ | 格納 IP が **10,000** を超えると速やかにクリーンアップ |

## 静的フロントエンド スキップ

**GET** と **HEAD** のみ、次のパスは認証失敗バンと匿名レート制限をスキップします（同時上限には 引き続き数えられます）:

| パス パターン |
|---------------|
| `/`           |
| `/index.html` |
| `/assets/*`   |
| `/js/*`       |
| `/css/*`      |
| `/svg/*`      |

API ルート、Maven リポジトリ パス、その他のメソッドは **スキップされません**。

## ステータス コード（このミドルウェア）

| コード | いつ                                 |
|--------|--------------------------------------|
| 429    | 匿名 IP がトークンバケット制限を超過 |
| 403    | 401/403 が多すぎて IP がバン         |
| 503    | プロセスの同時リクエスト上限超過     |

本文は多くの場合空。ステータス コードを信頼。現在 `Retry-After` ヘッダーはありません。

## クライアント向け指針

1. 高頻度やスクリプトのトラフィックでは認証アクセス（セッション Cookie、Basic、Bearer）を優先し、IP ごとの 匿名バケットを避けます。
2. タイトなログイン / プローブ ループを避ける: 1 IP からハンドラ級 **401/403** が **5** 回で最大 **約 5 分** バンされます。
3. リバース プロキシや CDN の背後では、`trusted_proxies` と `cdn_ip_header` を正しく設定し、プロキシ単位ではなく
   実クライアント単位で制限します。
4. **429** ではバックオフ（例: 指数）してから未認証の再試行。
5. この層からの **503** はインスタンス飽和。後で再試行するか、適切なら `max_active_requests` を上げる / スケール。
