# キャッシュ方式

RenoP は既定でメモリキャッシュを使用します。管理者はサービス設定で Redis または Valkey を選択できます。
方式の変更は再起動後に有効になります。

## 設定

```yaml
cache:
  mode: memory
  address: localhost:6379
  username: ""
  password: ""
  database: 0
  tls: false
  timeout_ms: 1000
```

`mode` は `memory`、`redis`、`valkey` に対応します。`address` は `host:port` 形式で、IPv6 は角括弧で囲みます。
ユーザー名は省略可能です。パスワード認証と TLS に対応し、TLS はサーバー証明書を検証します。
データベース番号は 0–65535 の範囲で、接続先サービスに存在する必要があります。
`timeout_ms` は 10–10000 ミリ秒で、接続、プール待機、読み取り、書き込みに適用されます。
接続プールの上限は八接続です。外部方式を選択した場合、起動時に接続できる必要があります。

## キャッシュ対象

方式はアーティファクトのメタデータ内容、解析済み Maven メタデータ、認証結果、データベースの
アカウント、セッション、プロフィール、識別情報の検索、リポジトリのキャッシュ方針、
上流 Docker トークン、SPA リソースに適用されます。生成した HTML も対象です。
永続ストレージ、稼働中のセッション、ロック、接続、ワーカーの管理方法は維持されます。

外部の値はプロセス固有の鍵で暗号化し、完全性を検証します。キャッシュキーに認証情報やリクエストパスは含まれません。
ローカルの索引には容量管理と対象を絞った無効化に必要な項目だけを保持します。
遠隔削除に失敗しても、認証情報を取り消す際に参照を破棄します。
無効化前に開始した認証処理がキャッシュを再登録することも防ぎます。

既存の容量上限と論理的な有効期限は維持されます。ファイル容量は
`server.file_cache_size_mb` に従います。外部の値は一件最大 2 MiB、最長 24 時間で失効し、
ファイル、方針、SPA の値は一時間で失効します。キャッシュサーバー側で総メモリ上限と
削除方針を設定してください。RenoP は共有サーバーの設定を変更しません。

キャッシュ再起動、削除、欠損、暗号文の検証失敗、実行中の接続障害では、データベース、
ストレージまたは生成処理に戻ります。接続障害後は五秒間キャッシュを迂回して再試行します。
RenoP を再起動すると新しい名前空間と鍵が作られ、古い値は期限に従って削除されます。
キャッシュ値を正本として扱うことはありません。

## 管理 API

```http
GET /api/settings/cache
PUT /api/settings/cache
POST /api/settings/cache/test
```

システム管理者または `admin:settings` を許可されたトークンが必要です。
GET と PUT は保存済みパスワードを返しません。`password_configured` は設定済みかを示し、
`restart_required: true` は変更に再起動が必要なことを示します。空のパスワードは既存値を維持し、
`clear_password: true` は保存済みパスワードを削除します。

PUT は上記の項目を受け付けます。テストは同じ設定を使い、省略したパスワードを維持して、
保存せずに接続を確認します。リクエスト本文の上限は 8 KiB です。
安定したエラーコードは `cache_settings_invalid`、`cache_settings_save_failed`、`cache_connection_failed` です。

キャッシュアカウントには `renop:*` に対する PING、SET、GETRANGE、DEL と、サーバーが必要とする
認証・データベース選択コマンドの権限が必要です。この API では Sentinel やクラスタ検出は設定しません。
