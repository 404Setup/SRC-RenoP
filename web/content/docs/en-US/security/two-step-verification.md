# Two-step verification

## Login behavior

Configure two-step verification in the account security panel. After a successful password or third-party login, RenoP requires a configured second factor before issuing a browser session. With an authenticator and a secondary Passkey both enabled, either may complete this step. A Passkey assigned to second-factor use cannot sign in on its own. A primary Passkey can still be followed by an authenticator code.

Password and primary Passkey login return `409` with `X-Renop-Error-Code: MFA_REQUIRED` when a second factor is needed. GitHub returns to `/account/login?mfa=1` with the local `return_to` destination. The private HttpOnly `renop_mfa` cookie authorizes only the pending verification endpoints; it is not a browser session. Challenges expire after five minutes, are single-use, and are discarded on restart. The process retains at most 4,096 challenges and eight per account.

## Authenticator setup

Choose **Set up** beside **Authenticator app**. Scan the displayed QR code or enter the displayed key manually using time-based codes, SHA-1, six digits, and a 30-second period. The QR image is generated by RenoP; setup material is never sent to an external QR service. Confirm with a code from the app within five minutes. An unconfirmed setup does not change login policy.

Codes follow [RFC 6238](https://www.rfc-editor.org/info/rfc6238/) and accept one time step before or after server time. Keep server and device clocks synchronized. A successfully used counter cannot be reused, including the setup confirmation code; wait for the next code when necessary. Five rejected codes in a five-minute account window block further code attempts until that window ends. New login challenges do not reset the limit.

## Passkey as a second factor

Register a Passkey in the account before enabling **Passkey as a second factor**. Password login or a connected third-party account must remain available as a primary method. RenoP prevents disabling that last primary method or deleting the last secondary Passkey while this option is enabled. Disable the option before removing its last Passkey. Secondary assertions require WebAuthn user verification.

## Verification API

All JSON POST/PUT bodies below require `Content-Type: application/json` and are limited to 4,096 bytes. Profile mutations require the current browser cookie and a sign-in from the last five minutes; an older session receives `MFA_REAUTH_REQUIRED`. Successful changes revoke other browser sessions. The profile security response adds the booleans `totp_enabled` and `passkey_second_factor` and never includes the authenticator key.

| Method | Path | JSON body or result |
|---|---|---|
| GET | `/api/auth/mfa` | `{totp,passkey,expires_at}` |
| DELETE | `/api/auth/mfa` | `204` |
| POST | `/api/auth/mfa/totp` | `{"code":"012345"}` |
| POST | `/api/auth/mfa/passkey/begin` | `{}` → `{options}` |
| POST | `/api/auth/mfa/passkey/finish` | `{credential}` → session |
| POST | `/api/auth/profile/mfa/totp/begin` | `{}` → `{id,secret,uri,qr,expires_at}` |
| POST | `/api/auth/profile/mfa/totp/confirm` | `{"id":"setup-id","code":"012345"}` → security |
| PUT | `/api/auth/profile/mfa` | `{"passkey_second_factor":true}` or `{"totp_enabled":false}` → security |

```json
{"totp_enabled":true,"passkey_second_factor":true}
```

Codes, QR images, setup keys, and challenge cookies must not be placed in URLs, logs, or browser storage. Verification errors use `MFA_INVALID`, service failures use `MFA_UNAVAILABLE`, and a standalone secondary Passkey returns `MFA_PRIMARY_REQUIRED`. A successful verification returns session details as JSON and sets the normal HttpOnly browser session cookie.

## Recovery and operation

Four unused offline recovery codes reset the password, remove the authenticator, turn off Passkey second-factor mode, and revoke all browser sessions in one transaction. Registered Passkeys remain attached and become available for primary login. Email password recovery preserves second-factor settings. Keep offline recovery codes in a safe place and reconfigure two-step verification after account recovery.

Accounts with any second factor must use API tokens for package clients and automation; account passwords are rejected on protocol authentication paths. Existing scoped and migrated upload tokens continue to follow their permissions. Disabling two-step verification restores password protocol access if password login is enabled.

RenoP creates the private top-level `mfa_encryption_key` in its configuration at startup. Authenticator keys are encrypted with AES-GCM and bound to immutable account IDs; the key is excluded from settings responses. Back up the configuration together with the database and preserve this key when moving the instance. Losing the key prevents authenticator verification; use offline recovery codes to restore access.
